## Finding

The Windows graph omitted `@expo/xcpretty`, so the strict stale-exception rule correctly
rejected its ordinary exception entry. The clean Linux install used by required CI still
reported the same high-severity transitive Expo build-tool row and correctly rejected it as
undocumented after removal. A single advisory can therefore be present or absent across the
two supported audit environments at the same lock revision.

## Bounded Correction

The policy now supports `conditionally_reported_packages` only when an exception also has a
non-empty `conditional_reason`. Conditional coverage:

- is limited to explicitly named packages;
- still expires on `review_by`;
- still enforces `maximum_severity`;
- still appears in the accepted-exception report when observed; and
- does not disable stale detection for ordinary exception packages.

Only `@expo/xcpretty` uses this field. No dependency, lockfile, runtime, release, or application
behaviour changes.
